# Decision log

Format: decision. Why. Alternatives rejected.

- **Simulator: MuJoCo (CPU, local).** MJCF is plain XML an agent can write and validate; runs natively on Mac; matches HUD's stack (rua-envs is mostly MuJoCo, their pipeline is Newton + MuJoCo); agents don't need high-fidelity rendering. Rejected: Isaac Sim (heavy, GPU-only, rendering-focused), ManiSkill3/RoboTwin (Linux/GPU-leaning), Genesis and Newton (still to compare in the trade-off write-up).
- **Robot: Franka Panda (MuJoCo Menagerie).** Standard single arm, used across rua-envs. Rejected: bimanual (more complexity, no clear capability payoff yet).
- **Generator input: text first, image later.** Text is the assignment's primary input; real-to-sim from images is a stretch goal.
- **Target band: 5-30% agent success (HUD's definition), kept deliberately. REVISIT.** It's HUD's stated bar for a good task. Literature puts the max learning signal near 50% (p(1-p) variance; DAPO, Online Difficulty Filtering keep ~25-75%), so 5-30% is a harder-than-optimal band. Our reason to keep it: tasks are meant to expose RUA failure modes, not just maximise training signal. Open question to raise with Lukass. Note: 10 runs can't separate 5% from 30%; calibration needs ~20-30 runs on borderline tasks.
- **Arm control: mink IK + interpolated joint targets.** Menagerie Panda only has joint position actuators. IK keeps real reachability/collision failures visible to the agent (we report end error). Single-jump setpoints dropped a grasped cube in testing; interpolating fixed it. Rejected: mocap weld (hides reachability), OSC (needs torque actuators, more tuning).
- **Robot assets via `robot_descriptions` (cached Menagerie), not vendored.** Zero files in repo, pinned upstream. Rejected: git submodule (large), copying XML.
- **Scene built in code with MjSpec on top of untouched Menagerie panda.xml.** One place to add tables/objects/cameras programmatically, which the generator will need. Rejected: hand-edited XML templates.
- **Camera: one over-the-left-shoulder view by default; wrist camera only when a task needs it.** Image axes roughly match robot axes, so frame confusion isn't baked into every task. Offset sideways because straight-behind views are blocked by the arm. More views make tasks easier and cost tokens, so one view is the cheap, honest default. Mirrored/other viewpoints become a deliberate difficulty knob. Rejected: front-facing view (mirrored, accidental frame confusion), shoulder+wrist always on (2x image tokens).
- **Grade the final state, not the first frame success flickers true.** The env never terminates early; the bridge checks success when the agent stops. Catches "lifted then dropped" and transient successes (LIBERO's latch counts these). Rejected: terminate-on-first-success.
- **HUD SDK does the loop and motion.** `env.gym` + `DirectControl` serve `move_to`; DirectControl interpolates targets per tick, so the sim only does IK + physics per tick. Orientation is a quaternion in the contract; the SDK exposes roll/pitch/yaw to the model. Rejected: our own agent loop or tool server.
- **Contract lives in code (tabletop.py), not a JSON file; cameras are a launch-time switch (WRIST=1).** The contract must match the observation exactly, so they sit together. HUD fixes observed images per env process, so camera choice can't be a per-task arg (same as rua-envs' BENCH_CONTROL). Rejected: one JSON per camera config.
- **Default cameras: top-down + wrist (CAMERAS env var); shoulder view kept as a "hard" knob.** Top-down maps table x/y straight to image x/y, removing the depth guessing that sank luna (0/10, shoulder-only). Wrist covers the moment the arm hides the cube from above. Same layout as the Bitter Lesson real-robot study (overhead + wrist). Rejected: depth image (extra tokens, predicted depth is noisy), pixel-to-world tool (maybe later, a harness knob).
- **Arm starts parked (pulled back/up), not at Menagerie home.** Home pose hovers right over the workspace and hid the cube from the top camera.
- **Grasp line on every move result, copied from HUD's libero env.** "open" / "fingers met; nothing between them" / "fingers did not meet". Luna ignored the raw gripper number; HUD and JustRUA both expose grasp feedback. Fair: a real gripper reports finger position.
- **Validate the harness before tuning difficulty.** A task setup counts only when (1) a scripted oracle through the real `move_to` tool scores 100% and (2) a stronger model does well on the easy version. Otherwise a low pass rate can't be told apart from a broken harness. The oracle (`rua/oracle.py`, run with HUD_LLM_MODEL=oracle) becomes the discriminator's solvability check. lift_cube oracle: 10/10.
- **Wrist camera mounted like real lab setups: on the wrist, above the hand, tilted down at the fingertips.** Fingertips sit at the bottom of the image, so the agent sees what the hand is doing and whether the object is between the fingers. Replaces a side-offset, straight-down camera that trapped luna in 4/8 failures (cube "centred" in image but ~7 cm off the fingers). Rejected: on-axis camera inside the hand (unrealistic), offset straight-down (the trap).
- **Grasp-point marker hidden.** MuJoCo drew the tcp site as a dot that acted as an aiming crosshair; aids like that change scores a lot (Anthropic: cursor tool 6% -> 32%), so it's off by default and can be a deliberate knob.
- **Tool notes state the orientation convention** (straight down = roll ±π, pitch 0; roll=0 points up). 2/8 luna failures set roll=0 and stalled.
- **Truth test (`rua/checks.py`) runs before any model, $0.** Each check puts the sim in a known state and verifies what the agent is told (notes, grasp line, stall line, camera layout) is true. One check per harness failure mode found; it becomes part of the discriminator. Rationale: all 8 luna failures traced to harness faults; no paper we found does this. First run caught a real bug (stale target after a stall) and a wrong assumption (yaw direction).
- **Harness fixes from the failure review:** binary gripper (>=0.5 open; an echoed 0.62 dropped the cube), plain stall line ("stopped X cm short: blocked or out of reach") instead of a bare residual, target reset to the measured pose after a stall, yaw direction stated in notes. **Run settings pinned and recorded in the job name:** STEPS=40 (literature 40-100), EFFORT=medium (effort alone moved one model 9% -> 33%).

## Generator and discriminator (Nov 23)
- **Tasks are YAML specs checked by a schema; fixed code builds the scene.** Literature: LLM-written task code usually runs but is often wrong, and object placement in reset() is the most common bug (AnyTask, GenSim). A spec restricts the generator to building blocks we trust, makes difficulty knobs plain fields, and is easy to diff and dedup. Rejected: LLM writes Python task code (GenSim/RoboGen style).
- **The generator is a coding agent (Claude Code) using `build` / `check` / `calibrate` commands.** Matches the assignment's "agent-native pipeline". Rejected: a fixed LLM API call inside the pipeline (less able to read failures and iterate).
- **gpt-6-sol defines the 5-30% band; luna is the cheap pilot.** Sol is the stronger, more representative target. Consequence: lift_cube (sol 85%) is too easy; tasks must be harder.
- **Object placement randomized per seed from ranges in the spec.** Stops agents memorizing a fixed scene and gives calibration real variance. The same sampler feeds the env and the oracle, so the oracle knows the poses without reading the sim.
- **Discriminator = gates, cheapest first; a failure goes back to the generator with the reason.** 1 schema, 2 physics settles (no overlap, falling, unreachable), 3 not solved at reset + do-nothing fails + random fails, 4 truth test, 5 oracle solves every seed, 6 strong model on easy setting, 7 calibrate knob on sol into 5-30%, 8 failure review (harness vs model), 9 dedup. Free gates run on every spec; paid gates only after all free gates pass.
- **Physics fixes found by the oracle gate (not by any model run).** (1) Menagerie's gripper squeezed only ~2.5 N on a 5 cm object, so grasps held only at one wrist angle; made the actuator 10x stiffer (~25 N, under a real Franka's ~70 N). (2) Objects get condim=4 (twisting friction) so they don't pivot in the grip. (3) IK posture anchored to Menagerie's home pose; anchoring to the current pose let the wrist swing ~16 deg mid-lift and fling objects. Before: 3/15 aligned scripted lifts across yaws; after: all aligned lifts succeed. Earlier agent runs (luna 25%, sol 85%) were on the weak gripper, so they understate lift success at non-default yaws.
- **Oracle through the real HUD tool is a required gate, not just in-process.** It caught a grading crash (numpy bool not JSON serializable -> every run scored 0) that the in-process gates could not see.

## Assets (Nov 23)
- **Objects come from a closed, pre-checked set; specs reference them by type/ID only.** Every generator that produced usable tasks (RoboTwin-OD, GenSim2, RoboCasa) does this; none lets the task-writing LLM invent geometry inline. Three tiers: (1) primitives, (2) articulated templates built from boxes + a joint (drawer, door, lid; RoboCasa's recipe), (3) a curated catalog of ~20 scanned objects (mujoco_scanned_objects, CC-BY/MIT) with cards (id, size, mass, grasp axis, hollow). New catalog objects pass a one-time admission test (drop, rest, hollow probe, scripted grasp, one render). Rejected: live Objaverse retrieval (noisy scale/quality), text-to-3D per task (GPU, 15-30% of outputs unstable in sim), LLM-written meshes.
- **No deformables (towels, rope).** A parallel-jaw pinch can't hold flat cloth in MuJoCo (needs a fake "sticky" grasp), MuJoCo 4.0 just removed the old cloth/rope tools, and no LLM-agent baseline exists to compare against. Articulated objects give an untested failure family at far lower risk.
- **Drawer template: open-front cabinet of boxes + a drawer on a slide joint, with a pull tab handle.** A bar handle forced a front-to-back pinch and the Panda's ~20 cm-wide hand hit the cabinet; a tab sticking out is pinched from the sides and the hand stays clear. Drawer-cabinet contact is excluded (rails): a fixed cabinet counts as world, so MuJoCo's parent-child exclusion doesn't apply and the drawer jammed (20 N moved it 1.5 cm). Damping is the difficulty knob. Success = opened >= 90% of travel and at rest (RoboCasa/ManiSkill convention).
- **Oracle offsets are in the object's frame**, so "pull 18 cm" follows a cabinet rotated by the per-seed yaw.
- **Two more free gates, each from a bug the oracle caught:** `joints` (a 10 N pull for 1 s must open each drawer >= 50%; verified it fires on a stuck drawer) and `reach` (open gripper can come down onto every targeted object/part). They localise the cause, where an oracle failure only says "something broke".
- **Fixes from the sol drawer review (1/5, mostly model errors: grasping above the tab, shoving the drawer shut while regrasping).** (1) Tool notes now say which way the fingers close (yaw 0 -> along y, ±pi/2 -> along x); 3/5 episodes wasted steps discovering it; truth-test check added. (2) Reported state rounded to 1 mm/0.001: 4/5 episodes had 20 s timeouts; in sim, a hand pressing into the cabinet never satisfied DirectControl's "stopped" rule (change < 1e-4 for 2 ticks) with raw values, and does with rounded ones. Caveat: the new "pressing ends promptly" check passes with or without rounding (couldn't reproduce through the tool path on a cube), so it's a regression guard, not proof; the next drawer run's timeout count is the real test. Not fixed: grip slipping when an agent pinches only the tab's edge (judged real difficulty), IK getting stuck after large wrist pitches (to investigate).

## Three more tasks (Nov 23)
- **Physics: RK4 at 1 ms instead of Menagerie's implicitfast at 2 ms.** implicitfast damps the arm in a way the contact solver doesn't see, so every grasped object crept ~2 cm along the pads per lift (a 5 cm cube too; 3 cm pegs fell out). RK4 1 ms: <3 mm. Rejected: noslip / elliptic cones (no effect), Euler (arm stopped 2-4 cm short), RK4 at 2 ms (stiff gripper chattered, drawer tab slipped). Cost ~3x sim time. All old tasks re-verified (gates, checks, oracle via tool).
- **grasp_rotated_block: 12x3x4 cm bar, yaw 30-90 deg.** Below ~20 deg the bar fits the 8 cm opening without rotating, so 30 deg is the floor that forces a yaw match. Knob: yaw range (and bar length).
- **hole_block template: four box walls around a square through-hole, table as floor.** Fixed body placed like the cabinet; the hole side is a spec field so clearance is a plain number. Rejected: a mesh with a hole (MuJoCo collides meshes as convex hulls, which fills the hole).
- **peg_in_hole: 3x3x6 cm peg, 7 mm clearance, success = peg centre inside the hole and bottom >= 2 cm below the block top.** Peg kept short so it's grasped at its centre without touching the palm (taller pegs either hit the palm or pivoted in the grip). Knob: clearance (`hole` minus peg width).
- **Zone marker: thin cylinder with contype=0/conaffinity=0.** Visible, never collides, so the puck slides over it. Drawn so "puck fully inside the circle" matches the success radius (circle diameter = 2 x (radius + puck radius)).
- **push_to_zone: 10 cm puck (wider than the 8 cm opening), in_zone radius 5 cm and at rest.** Oracle pushes with the open fingers straddling the puck's centreline; a closed-finger point push let the puck slide off the line by up to 5 cm. Knob: zone radius / push distance.
- **Oracle steps can take `toward: <object>`:** offset x points from the step's object to that one, so a push follows the line between two independently sampled objects. Tool yaw is wrapped to [-pi, pi]; the real tool rejected 6.1 rad (caught only by the oracle through HUD, not the in-process gate).
- **Fixes from the drawer+peg review (drawer 2/10 and peg 1/5 judged mostly real difficulty; 0 timeouts after state rounding).** Grasp line now says "fingers blocked from opening" when an open command is held partly shut (7 episodes previously got no line); gripper reading clipped to [0, 1] (contact pushed it to 1.3). "Arm stuck after a big wrist tilt" was a fair reach limit (pitch -90 deg near the base is 11-13 cm unreachable, stall line reports it) and recovery works; kept as a truth-test guard. Not fixed, judged fair: grip slipping on an edge pinch; a held peg shifting when pressed on the block (a real robot isn't told either).
- **Precision knobs must be validated through the real tool, not just the sim oracle.** push_to_zone at 1 cm passed the in-sim oracle 5/5 but the tool-path oracle 0/5: DirectControl ends a move within ~1 cm of the target, so the task was unsolvable as served and sol's 1/5 on it was meaningless. Rule: a knob value is only legal if the tool-path oracle passes it. Push set to 1.5 cm (oracle 8/8).

## Four harder tasks: chaining, ordering, frames, tool use (Nov 23)
- **Why these four:** sol saturates single-step tasks and precision knobs hit the tool's ~1 cm floor. Chaining (LIBERO-10 bowl-in-drawer 7%), relative placement in a non-camera frame (RoboSpatial context 5.7%) and tool use are where frontier agents fail. Knobs are step/object counts, not tolerances. Rejected: tighter tolerances on existing tasks.
- **New predicates `closed`, `inside`, `stacked`, `near_offset`, `unmoved`; each still plain bool on the final state.** `stacked` and `inside` also require that the arm isn't touching the objects (contact check), so "holding it in place" doesn't count; `near_offset`/`stacked` require the object on the table or the block below. Rejected: a gripper-open check (fingers can be open and still pressing).
- **drawer_store_close: open, place, close, from a closed drawer (20 oracle moves).** `start` (drawer opening at reset) is the knob: 0 = three subgoals, 1 = two. Success = block centre in the tray, drawer <= 5% open, both at rest.
- **stack_ordered: 3 cubes of 4.5 cm, order given bottom to top.** Each pair must be within half a block in xy and one block-height (+-1 cm) in z. Knob: number of blocks, block size. Half a block (2.25 cm) is above the tool's ~1 cm error.
- **place_relative: "10 cm to the left of the blue cube, for a person across the table facing the robot" = -y.** "Left" is unambiguous once the viewer is given; "in front of" was rejected because it is ambiguous even for humans. The robot's-left spot is kept free so the camera-frame answer can be made, and fails. 3 distractors, 3 cm radius (3x tool error), `unmoved` 3 cm on the others. Knobs: frame (robot / opposite person / object-centric), distractor count.
- **Table extended to x=1.15 (was 0.95).** Measured: tcp reaches x <= ~0.90 at table height even with a tilted wrist (straight down ~0.80), so a cube on the old table at 0.85-0.9 could be grabbed directly. The cube sits at x 0.96-0.99, and direct grasps at 5 wrist pitches never moved it. Other tasks' objects are unaffected (gates pass); only the image background changes.
- **hook_retrieve: L-hook (40 cm handle, 12 cm crossbar, 50 g) as one free body of two boxes (`hook` shape, `handle` part).** Gripped 5 cm from its end, the crossbar reaches 33 cm past the hand. Cube and circle y ranges are kept to +-2 cm so a straight pull lands it (4 cm radius). Knobs: cube distance past reach, hook length.
- **Hook torsional friction 0.1 (MuJoCo default 0.005).** MuJoCo's torsional friction is soft: at the default the gripped hook pivoted about the finger axis until it lay on the table, the same for 20 g and 100 g, and shoved the cube away. 0.1 holds 50 g within ~1 deg. Applied to the hook only. Rejected: elliptic cones globally (would need every task re-tuned).
- **Knob values can be categorical (`dict[str, float | str]`)** so frame type can be recorded.
- **Fixes from the drawer_store_close/stack/hook review.** drawer_store_close 0/5 was partly unfair: 2/5 runs read the closed cabinet's top as an open drawer and the prompt never said the drawer starts closed. Prompts now state starting states, enforced by a schema rule (any task with a drawer must say "starts closed/open"). The grade now also records each success condition separately (e.g. inside=True, closed=False), so a 0 says which part failed. Stack and hook failures were model errors (blocks released too low and sliding off; hook slipping or abandoned), kept as real difficulty. place_relative v2 (person at the robot's side: a 90 deg frame rotation, 5 distractors): sol 2/5 (v1 3/5).
- **New free gate `robust`: the oracle must still succeed with its placements 5 mm off** (4 directions, 3/4 must pass). peg_in_hole at 7 mm clearance needed ~3 mm accuracy (oracle 8/16 at 5 mm off, 0/16 at 10 mm) while the tool stops within ~1 cm: sol's 0/10 measured the harness, not the model. Peg hole widened to 15 mm clearance (oracle 16/16 at 8 mm off). Found without trace access (Chrome disconnected) by a free sim sweep. Rejected: tuning precision by sol pass rate alone (it can't tell an impossible task from a hard one).
- **run.py reports k/n with a 90% Wilson interval and a band verdict, and logs every run (settings, job id, estimated cost) to runs/log.jsonl.** Exact cost per trace is on hud.ai; the SDK doesn't expose it. SEED0 gives confirmation runs fresh seeds (earlier batches reused seeds 0-4).
- **Peg v3: 11 mm clearance + peg starts rotated 20-70 deg** (v2 at 15 mm: sol 8/10, so peg's earlier "difficulty" was purely the 7 mm precision cliff). Passes the robust gate and the tool oracle 5/5.
- **run.py counts errored rollouts separately and marks the run INVALID.** A spec typo (a list in `knobs`) made every rollout crash at reset, and the runner reported "0/5 unclear", indistinguishable from a hard task.
- **Generator feedback is part of the loop:** the generated task's agent reported prompt gaps (part offsets ignore a drawer's `start`; gripping moves parts; one predicate per kind), now in docs/generator_prompt.md. Missing blocks (multi-object `inside`, `under`) are logged as the next building blocks rather than faked in a spec.
- **Traces saved locally (runs/traces/<job>/, images stripped).** Trace review depended on the browser extension, which dropped for hours overnight; the SDK can upload traces but not fetch them, so the runner keeps its own copy. hud.ai stays the place for videos and exact cost.
- **New free gate `visible`: every object starts >= 5 cm inside the top camera's view.** From the hook review (cube pushed out of view in 4/8 failures). It flags hook_retrieve v3 (cube at x 1.03-1.06, at the view's edge), so v3's 15% is partly a harness effect. Not re-tuned overnight: model spend reached the $30 cap (true sol cost is $0.13-0.16/episode from trace pages, above the $0.12 estimate). Fix for later: keep the cube in view (x <= ~1.0) and find difficulty another way, or widen the top camera for all tasks (requires recalibrating everything).
- **Grades carry the numbers behind them (`final_state`: object positions in mm, drawer open fraction, whether the arm still touches each object).** Reviewers couldn't tell "drawer 6% open" from "never opened" from the pass/fail conditions alone.
