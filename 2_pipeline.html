Pipeline design

The pipeline turns a one-line intent into a checked MuJoCo task. An LLM writes the task. Code decides whether it is any good.

flowchart LR
    I[Intent<br/>one line, or a photo] --> G[Generator<br/>LLM writes a YAML spec]
    G --> F{Free checks}
    F -->|fails, with the reason| G
    F -->|passes| H[Human approves]
    H --> P{Run the target model}
    P -->|too easy or too hard| G
    P -->|hard enough| T{Read the traces<br/>and replay them}
    T -->|the model failed| L[(Task library)]
    T -->|my harness failed| K[Fix it,<br/>add a free check]
    K --> F

Generator

python rua/generate.py "test whether the agent can ..."

The model writes a YAML spec and nothing else: the objects, where they can start, what counts as success, a scripted solution, and the difficulty knobs. Fixed code builds the scene from it.

Why a spec and not code. Every earlier system I read has the LLM write task code, and they report the same weak point. In AnyTask the most common error is in reset(), where objects get placed. GenSim lists made-up assets as its first implementation error. RoboGen lost 13 of 155 tasks to broken scenes. Those are all things code can do deterministically, so I took them away from the model. It chooses what goes in the scene; code decides where things land.

Why a closed set of building blocks. GenSim2 found that composing tasks from parts already known to work beats asking the LLM to break a task down from the top (0.68 against 0.54 solution rate). Each of my blocks is tested once and reused. The model cannot invent an asset.

Why failures go back with the exact reason, for up to five rounds. RoboTwin 2.0 runs the same loop and needs 1.76 rounds on average. Mine took 1 to 5.

Why a photo is an optional input. The brief asks for it. rua/intent.py maps what it sees onto my building blocks and refuses anything that doesn't fit, so a photo can't smuggle in an object we have never tested.

What it can build. Boxes, cylinders, spheres, a hook, a drawer, a block with a hole, a ledge, a seesaw, a box with a sliding lid, painted zones, and scanned household objects from a small catalog. Also hidden weights, slippery surfaces, seeds where the task is impossible, and goal images.

Discriminator

The usual funnel in this literature is: the code compiles, it runs, the generator's own solver finishes the task, a person or a vision model looks at it. That proves a task can be solved. It does not prove the grader is right. I found no generator paper that checks whether a robot doing nothing can pass.

Benchmarks outside robotics show why that matters. In τ-bench a trivial agent passes 38% of tasks (Agentic Benchmark Checklist). OpenAI audited the SWE-bench Verified problems that o3 kept failing and found 59% had flawed tests. So most of my checks are aimed at the grader and the harness, not the scene.

Cheapest checks run first. Anything that fails goes back with its reason.

Check What it catches Why it's there
Schema and prompt lint Missing fields; a prompt that doesn't state the success threshold An agent can't hit a threshold it was never told
Settle, joints, reach, visible Objects that fall at the start, a jammed drawer, things the hand can't reach or the camera can't see Each one caught a real bug in my own scenes
Trivial Tasks that pass if the robot does nothing or moves at random The missing negative control described above
Oracle The scripted solution works, in the sim and through the real tool Standard practice (GenSim, GenSim2), with the addition that it must go through the same tool the agent uses
Robust The solution still works with every placement 5 mm off The tool only stops within about 1 cm. A peg task at 7 mm clearance passed the oracle, and sol's 0/10 on it measured my tool, not sol
Truth test (15 checks) Whether everything the agent is told is true All eight of luna's first failures were things I had told it wrong
Asset admission A scanned object that can't be gripped, won't release, or doesn't rest flat Same idea as the truth test, for objects
Model run How hard the task is for the target model Only a model can measure difficulty
Trace review and replay Whether a failure is the model's or mine See doc 3. Half my hard results failed this

Two choices inside that table:

  • Code does the judging, and a person takes one look. I did not use a vision model as the judge. RoboTwin 2.0's reached an F1 of only 0.30 and called misaligned stacks successes. GenSim gets by with about ten seconds of human review per task, so I kept a human approval step with a one-page review sheet.
  • Success requires the object released and at rest. ManiSkill requires the robot to be still for the same reason: it stops an agent from scoring by passing through the goal.

Each model run also reports three counts: failures that hit the step cap, failures where the arm jammed, and failures that stopped just short of the step budget. A low score is not read as "hard" until the first two are zero and the third has been read.

On the target difficulty. The brief asks for tasks an agent passes 5-30% of the time. As we discussed, I measured it on Astra and treated the range as a guide: lower is fine for this project as long as the failure is real. So a task at 0% stays in the set if the traces show an honest failure, and I spent the effort on proving the failures are real. For sample size, simple binomial arithmetic says 10 episodes cannot tell 5% from 30%, so the sol calibrations used 20 or more.

Harness

What the agent sees and does matters as much as the model. JustRUA raised one benchmark from 29.7 to 50.3 by changing only the harness. So each harness choice follows a measured result where I could find one.

Choice Why
move_to with absolute end-effector poses JustRUA found relative targets do not beat absolute ones (33.9 against 38.0 overall). move_joints would make the model do the arm's geometry in its head, with no evidence that LLMs can. The SDK serves one motion tool per environment, so it would be a launch setting. I scoped it and did not build it
Images after every move Showing images only on request dropped success from 83% to 68.5% (PyRUA-Lean)
Two cameras, top and wrist More cameras are not reliably better: a third view changed scores by -3.6, +5.8 and +10.7 across three models (Anthropic). In my runs one angled camera left luna unable to judge depth, and the wrist view fixed it
A plain-words grasp line ("fingers met; nothing between them") On real arms 32-64% of grasps close on nothing, depending on the model (Bitter Lesson)
A line saying when a move stopped short In the LIBERO-10 study arms reached only 64-72% of the commanded distance, and models could not work out why
Full history, medium effort Keeping the full episode history lifted JustRUA's score from 29.7 to 34.7, and it ran at medium effort. High effort changed nothing in my one test
Grading on the final state, hidden from the agent Models claim success on 24-39% of unfinished subtasks (RoboARCade), so the agent's word cannot be the grade
MuJoCo with the Menagerie Panda and mink IK, moves interpolated A local benchmark showed that commanding a pose as one jump dropped a held cube, and interpolating kept it

The five tasks

Task Spec Generator Astra Rollouts
max_overhang tasks/max_overhang.yaml Regenerated from one line 5/18 1, 2, 3
balance_sort tasks/balance_sort.yaml Regenerated from one line 1/12 1, 2, 3
weighted_overhang tasks/weighted_overhang.yaml Failed after 5 rounds 0/12 1, 2, 3, 4
balance_pick tasks/balance_pick.yaml Regenerated from one line 1/5 1
overhang_or_impossible tasks/overhang_or_impossible.yaml Regenerated from one line 3/5 1

All five pass every free check, and the scripted solution works 5/5 through the real tool.

I wrote the five specs by hand first, and the rollouts above ran on those. Then I gave the generator one sentence for each and let it write its own version from scratch.

It produced four of the five, and each of its versions passes every check and has a working scripted solution (tasks/generated/). To see whether a generated task is as hard as mine, and not just a look-alike, I ran Astra on all four.

Task Mine Generated Rollouts
max_overhang 5 of 18 2 of 5 job
overhang_or_impossible 3 of 5 4 of 5 job
balance_sort 1 of 12 0 of 5 job
balance_pick 1 of 5 4 of 5 job

Three of the four came out about as hard as mine. The generator also made its own choices along the way: it colour-coded the circles in one balance_sort version where I used left-to-right order, and it added a height check to max_overhang that I hadn't thought of.

balance_pick came out much easier, and the reason is useful. The generator built a gentler seesaw: the pivot is half as high, so the plank tilts less, and the swing is damped ten times more. My version's difficulty was cubes sliding off a plank that tips sharply, and the generated one mostly removed that. So the difficulty of a task can sit in a few physical numbers that the one-line intent never mentions. This is what the calibration step is for: run on Astra, a version this easy would go back to the generator rather than into the library.

Getting the balance tasks right took one fix. The generator's first versions laid the plank lengthways, which made Astra turn its wrist a quarter turn about three times per attempt and set off the wrist jam described in doc 3 in 6 of 10 attempts. I added one line to the generator's instructions, to lay long objects crossways. The next versions did, and Astra's arm did not jam once in 10 attempts.

The one task the generator could not produce was weighted_overhang. Its scripted solution has to stack four off-centre blocks so that the tower still stands when every placement is 5 mm off. It did not find one in the rounds I gave it. Writing scripted solutions for physically delicate tasks is the generator's weak point, and doc 3 comes back to it.

To run one: TASK=max_overhang HUD_LLM_MODEL=gpt-6-astra STEPS=60 EPISODES=5 python rua/run.py

What I turned down

The other option What I did Why
Have the model write the simulation code for each task, as most earlier systems do The model fills in a short description of the task (which objects, where they can start, what counts as success). Code I wrote once turns that description into the scene When models write the scene code themselves, it usually runs but puts objects in the wrong place or uses objects that don't exist. AnyTask, GenSim and RoboGen all report this as their most common failure. A description can be checked line by line before anything is simulated
Let the model invent any object it wants The model picks from a fixed list of objects that I have each tested GenSim2 found that building tasks out of parts already known to work succeeds more often than letting the model design from scratch (0.68 against 0.54)
Use a vision model to look at the result and judge whether the task is good Checks written in code, plus one look by a person before a task is accepted Vision models are poor judges here. In RoboTwin 2.0 the judge called misaligned stacks a success
Treat "a model solved it" as proof that the task works Every task comes with a scripted solution that must succeed through the same tool the model uses If a model fails a task, that alone can't tell you whether the model or the task is at fault. A scripted solution settles that before any model runs
Give points for progress along the way Grade only the final state of the table A robot can pass through the goal position without ever finishing the task. Grading the end state can't be fooled that way
